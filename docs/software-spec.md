\# Software Specification

\## Система управления вендинг-аппаратом DION ABA1



\*\*Статус:\*\* итоговая рабочая спецификация для проектирования и разработки ПО  

\*\*Основа:\*\* консолидированное ТЗ на ПО, архитектурная декомпозиция, state machine операций, recovery logic, структура БД и контракт интеграции с оборудованием



\---



\## 1. Назначение системы



Программное обеспечение предназначено для управления вендинг-аппаратом DION ABA1 барабанного типа с электронными замками и обеспечивает:

\- выдачу ТМЦ / СИЗ / расходных материалов;

\- возврат ТМЦ;

\- загрузку / пополнение;

\- управление барабаном и замками;

\- идентификацию пользователей по RFID и PIN;

\- учет остатков;

\- журналирование операций, событий и аудита;

\- экспорт данных;

\- сервисный режим;

\- восстановление после сбоя.



Система должна работать автономно в закрытом контуре без обязательного доступа в Интернет.

\## 5. Основные функциональные сценарии



\### 5.1. Выдача

Пользователь авторизуется, выбирает доступную позицию, система валидирует права и остаток, перемещает барабан, открывает нужную ячейку, ожидает действия пользователя, после подтвержденного завершения списывает остаток и завершает операцию.



\### 5.2. Возврат

Пользователь авторизуется, выбирает позицию для возврата, система валидирует право возврата, определяет ячейку возврата, перемещает барабан, открывает ячейку, ожидает завершения действия пользователя и только после подтвержденного завершения увеличивает остаток.



\### 5.3. Пополнение

Оператор запускает сервисную сессию пополнения, переводит аппарат в сервисный режим, последовательно выбирает ячейки, перемещает барабан, вводит фактическое количество и фиксирует изменения остатков отдельными атомарными подоперациями.



\### 5.4. Инвентаризация

Оператор/администратор просматривает остатки, сверяет фактические значения, выполняет корректировку только с обязательным комментарием и с записью в аудит.



\### 5.5. Сервисный режим

Сервисный режим предоставляет доступ к диагностике, ручному позиционированию барабана, тестам замков, дампу диагностики, backup/restore и recovery-разборке.

\## 8. State machine операций



\### 8.1. Выдача

Успешная ветка:



`created`

→ `authorized`

→ `validation\_in\_progress`

→ `validated`

→ `queued\_for\_execution`

→ `positioning\_requested`

→ `positioning\_acknowledged`

→ `positioning\_in\_progress`

→ `positioning\_completed`

→ `unlock\_requested`

→ `unlock\_acknowledged`

→ `unlock\_completed`

→ `user\_action\_pending`

→ `completion\_verification`

→ `inventory\_write\_pending`

→ `inventory\_written`

→ `completed`



Дополнительные состояния:

\- `rejected`

\- `cancelled`

\- `timed\_out`

\- `failed`

\- `recovery\_required`



Ключевое правило:  

\*\*остаток списывается только после подтвержденного завершения операции.\*\*



\### 8.2. Возврат

Успешная ветка:



`created`

→ `authorized`

→ `return\_rules\_validation`

→ `return\_slot\_resolution\_in\_progress`

→ `return\_slot\_resolved`

→ `validated`

→ `queued\_for\_execution`

→ `positioning\_requested`

→ `positioning\_acknowledged`

→ `positioning\_in\_progress`

→ `positioning\_completed`

→ `unlock\_requested`

→ `unlock\_acknowledged`

→ `unlock\_completed`

→ `user\_action\_pending`

→ `completion\_verification`

→ `inventory\_write\_pending`

→ `inventory\_written`

→ `completed`



Ключевое правило:  

\*\*остаток увеличивается только после подтвержденного завершения возврата.\*\*



Ограничение:  

без отдельного датчика наличия предмета факт возврата не может быть доказан физически на 100%.



\### 8.3. Пополнение

Пополнение моделируется как \*\*сервисная сессия\*\* с атомарными подоперациями по ячейкам.



Успешная ветка сессии:



`created`

→ `authorized`

→ `service\_mode\_requested`

→ `service\_mode\_active`

→ `awaiting\_slot\_selection`

→ `slot\_selected`

→ `positioning\_requested`

→ `positioning\_acknowledged`

→ `positioning\_in\_progress`

→ `positioning\_completed`

→ `awaiting\_qty\_input`

→ `qty\_entered`

→ `balance\_update\_pending`

→ `balance\_updated`

→ `awaiting\_next\_action`

→ `awaiting\_slot\_selection` \*(цикл)\*

→ `session\_completion\_requested`

→ `session\_finalization\_in\_progress`

→ `session\_completed`



Ключевое правило:  

\*\*каждое изменение остатка по ячейке — отдельная атомарная подоперация.\*\*



\### 8.4. Recovery

Recovery запускается после старта системы и анализирует незавершенные операции/сессии.



Ключевые состояния:

\- `startup\_scan`

\- `recovery\_targets\_found`

\- `hardware\_state\_requested`

\- `recovery\_evaluation\_in\_progress`

\- `operation\_reconciliation\_in\_progress`

\- `manual\_confirmation\_required`

\- `manual\_reconciliation\_in\_progress`

\- `recovery\_actions\_commit\_pending`

\- `recovery\_actions\_committed`

\- `post\_recovery\_safety\_check`

\- `degraded\_ready`

\- `system\_ready`

\- `failed`



Ключевое правило:  

\*\*если система не может доказать успешность операции, она не должна автоматически считать ее успешной.\*\*

\## 10. Контракт интеграции с оборудованием



\### 10.1. Контроллер барабана

Нормализованные команды:

\- `connect()`

\- `disconnect()`

\- `ping()`

\- `get\_position()`

\- `move\_to\_position(position)`

\- `ack\_response()`

\- `get\_last\_status()`



Нормализованные статусы:

\- `accepted`

\- `busy`

\- `unknown\_command`

\- `result`

\- `completed`

\- `failed`

\- `timeout`

\- `communication\_error`



Ключевая логика:

\- двухфазное выполнение команды перемещения;

\- автоматическое квитирование внутри адаптера;

\- запрет новой команды перемещения до завершения предыдущей.



\### 10.2. Контроллер замков CU24

Нормализованные команды:

\- `connect()`

\- `disconnect()`

\- `ping(board\_address)`

\- `get\_lock\_status(board\_address)`

\- `unlock\_lock(board\_address, lock\_number)`

\- `get\_unlock\_time(board\_address)`

\- `set\_unlock\_time(board\_address, value\_ms)`

\- `get\_version(board\_address)`



Сервисные команды:

\- `unlock\_all(board\_address)`

\- `set\_baud\_rate(board\_address, baud)`

\- `initialize(board\_address)`



Нормализованные статусы:

\- `ok`

\- `failed`

\- `wait\_timeout`

\- `unknown\_command`

\- `checksum\_error`

\- `communication\_error`



Ключевая оговорка:  

\*\*успешный ответ на unlock не равен физически доказанному факту изменения состояния ячейки.\*\*



\### 10.3. RFID RusGuard R5-USB

Целевой режим интеграции:

\- сначала `usb\_api` или `usb\_com`;

\- клавиатурный режим только как запасной.



Нормализованный интерфейс:

\- `connect()`

\- `disconnect()`

\- `ping()`

\- `start\_listening()`

\- `stop\_listening()`

\- `read\_once()`



Нормализованные события:

\- `card\_detected`

\- `card\_repeated`

\- `card\_read\_error`

\- `device\_connected`

\- `device\_disconnected`



Правило хранения UID:

\- `HEX`, `uppercase`, без разделителей.



\### 10.4. HardwareFacade

Application-слой работает только через:

\- `hardware\_healthcheck()`

\- `get\_drum\_position()`

\- `move\_drum\_to\_position(position)`

\- `get\_lock\_board\_status(board\_address)`

\- `unlock\_slot(slot\_id)`

\- `start\_rfid\_listener()`

\- `stop\_rfid\_listener()`

\- `get\_last\_hardware\_snapshot()`

\## 13. Ограничения и честные допущения



\### 13.1. Возврат

Без физического датчика наличия предмета система не может доказать факт возврата на 100%.



\### 13.2. Замки

Факт ответа CU24 на unlock и факт реального завершения пользовательского действия — это разные вещи.



\### 13.3. RFID

Финальный выбранный режим подключения R5-USB на Raspbian должен быть подтвержден практическим тестом.



\### 13.4. Recovery

Recovery не имеет права “додумывать” результат операции без доказуемых оснований.
